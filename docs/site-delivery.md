# Разработка сайтов под ключ: запуск, хостинг и опциональная CMS

Решение для обсуждения и внедрения, 19 ноября 2026. Документация и лицензии проверены по официальным источникам; прототип сборки и установка CMS в рамках этой задачи не выполнялись. Цены ниже — предлагаемые ориентиры нашего предложения, не исследование рыночных тарифов.

## Выбор

**Стандарт: Vite для CSS/JS, обычная семантическая вёрстка, небольшой набор Twig-шаблонов и Grav + Admin для клиентов, которым нужно редактирование.**

Клиент выбирает до разработки:

1. **Без CMS:** готовый ZIP с HTML/CSS/JS/изображениями. Размещается как статический сайт. Изменения самостоятельно в коде, через своего специалиста или отдельным заказом.
2. **С CMS:** отдельный полностью собранный ZIP с Grav, панелью управления, нашей темой и настроенными полями. Размещается на совместимом PHP-хостинге. Клиент меняет заранее согласованные данные через браузер.

**Основной продукт в обоих режимах — работающий сайт под ключ:** разработка, адаптация под телефон, наполнение согласованными материалами, настройка хостинга, подключение домена, HTTPS, публикация и проверка. ZIP и исходники — комплект передачи и резервная копия. Самостоятельное размещение клиентом возможно по отдельной договорённости, но не является стандартным предложением.

Оба режима без нашего постоянно работающего сервера, общей базы клиентов и обязательного SaaS. Аккаунт хостинга и домен оформляются на клиента; мы настраиваем и запускаем. На стороне клиента не нужны Node.js, npm, Git или сборка фронтенда.

**CMS нельзя просто положить рядом с произвольным HTML и получить редактирование.** Поля должны быть связаны с шаблонами. В CMS-режиме страницы рендерит PHP, хотя CSS/JS уже собраны и браузер получает обычный HTML. Это другой готовый вариант поставки, а не два архива для слепой распаковки друг поверх друга.

## Сравнение трёх бесплатных open-source CMS

| Критерий | Grav + Admin | Bludit | Decap CMS |
|---|---|---|---|
| Лицензия | MIT у ядра и Admin2 | MIT | MIT |
| Хранение | Файлы, без отдельного сервера БД | Файлы/JSON, без сервера БД | Файлы в Git-репозитории |
| Поставка | Собранный ZIP на PHP-хостинг | ZIP на PHP-хостинг | Панель + настройка backend/auth + публикация сайта |
| Структура контента | YAML blueprints: поля, списки, медиа | Страницы, изображения; встроенные custom fields ограниченнее | Коллекции и поля в конфигурации |
| После изменения цены | Сохранение контента, без пересборки Node.js | Сохранение контента, без пересборки Node.js | Изменение файлов Git; для сгенерированного сайта нужна сборка/публикация |
| Настройка картинок, прайса, акций | Хорошо ложится на типовые схемы | Для удобных повторяемых строк/структур потребуется больше собственной логики | Хорошо, если уже принята инфраструктура Git и сборок |
| Итог | **Основной вариант** | Резерв для очень простых страниц/новостей | Не основной для модели «запустили и передали клиенту» |

Основания: [лицензия Grav](https://github.com/getgrav/grav/blob/develop/LICENSE.txt), [лицензия Admin2](https://github.com/getgrav/grav-plugin-admin2/blob/develop/LICENSE), [поля Grav](https://learn.getgrav.org/2/forms/blueprints/fields-available), [Bludit: устройство и MIT](https://github.com/bludit/bludit), [custom fields Bludit](https://docs.bludit.com/en/content/custom-fields), [лицензия Decap](https://github.com/decaporg/decap-cms/blob/main/LICENSE), [backend Decap](https://decapcms.org/docs/backends-overview/), [публикация Decap](https://decapcms.org/docs/editorial-workflows/).

Выбор Grav — инженерная оценка под нашу задачу: он чуть сложнее Bludit внутри, зато формы редактирования описываются декларативно, без написания своей админки для каждого клиента. Самая маленькая CMS по числу файлов не обязательно самая дешёвая в производстве сайтов.

В Bludit документированные встроенные custom fields имеют типы string/bool. Структуры вроде строк прайса с единицей измерения и сортировкой придётся моделировать страницами либо добавлять плагин/свой интерфейс. Это допустимо, но снижает выгоду для конвейера.

В Decap редактор сам по себе не публикует сайт: нужны хранилище, авторизация и механизм выпуска изменений. Для технического клиента с собственными Git/CI это хороший вариант; для остальных передача и восстановление сложнее выбранного PHP-пакета.

Дополнительный отсев: Automad не включён в тройку open-source кандидатов — текущий сайт прямо описывает лицензию как source-available с ограничением на конкурирующий SaaS. Бесплатность не тождественна открытой лицензии. [Официальное описание Automad](https://automad.org/).

## Сборка на нашей стороне

**Vite + vanilla JS/TypeScript + CSS; Twig — шаблоны; контент отдельно.** Не вводить React/Next/SPA и сервер Node для обычной визитки. Если достаточно HTML/CSS и нескольких обработчиков меню/галереи, на этом и остановиться.

Vite собирает стили и JS, выдаёт версионированные assets и manifest. Шаблон подключает их через маленький общий адаптер. Это штатный сценарий интеграции с серверным рендерингом: [Vite Backend Integration](https://vite.dev/guide/backend-integration). Сборщик не заменяет шаблонизатор и не превращает CMS автоматически в статику.

Предлагаемый способ избежать двух разных реализаций дизайна:

1. Один набор Twig-шаблонов, CSS/JS и схем контента для обоих пакетов.
2. На нашей машине временно запускается локальный Grav с реальным контентом. Он служит средой сборки и для будущего статического сайта.
3. Для CMS-пакета упаковывается готовый runtime с темой и данными.
4. Для статического пакета наш экспортёр сохраняет HTML всех явно перечисленных публичных маршрутов, копирует используемые ресурсы, нормализует ссылки и формирует sitemap/robots/404.
5. Статический результат проверяется отдельно через обычный HTTP-сервер без PHP. Ядро CMS, аккаунты, конфигурация и админка в этот ZIP не попадают.

Экспортёр — запланированный одноразовый внутренний инструмент, **не обещанная штатная функция Grav** и не уже существующая команда проекта. Не полагаться на случайный сторонний плагин экспорта как на обязательную зависимость. Ограничить первую версию небольшими сайтами с известными маршрутами, без поиска, личных кабинетов и серверных интерактивных страниц.

Так нейросеть меняет HTML-подобные шаблоны, CSS и YAML. Мы не поддерживаем параллельно отдельную HTML-версию и другую тему CMS. PHP и Grav нужны локально нам для сборки; покупатель статического пакета их не получает и не запускает.

Если общий экспорт на пилоте окажется дороже прямой сборки, не усложнять его до универсального генератора: сначала зафиксировать ограниченный набор поддержанных компонентов и маршрутов. Это точка проверки решения до массового производства.

## Как организовать конвейер

1. Из утверждённого концепта Stitch сделать чистые адаптивные шаблоны. HTML Stitch — материал для переноса: проверить внешние ресурсы, CDN, реальные контакты, выдуманные факты и различия desktop/mobile. Не отдавать его без проверки как готовый сайт.
2. Заполнить карточку сборки: клиент, домен, язык, страницы, пакет, редактируемые сущности, изображения, контакты, форма/получатель, SEO, список старых URL и редиректов.
3. Выбрать модули из небольшого набора: hero, услуги, прайс, галерея, акции, FAQ, контакты. Менять оформление и композицию под концепт, сохраняя общий контракт данных.
4. Собрать assets, отрендерить страницы, сформировать нужный ZIP и исходники. Версии runtime/плагинов фиксировать; точные версии и лицензии включать в паспорт выпуска.
5. Проверить результат на тестовом хостинге того же типа, согласовать приёмку, развернуть на хостинге клиента, подключить домен/HTTPS и передать доступы и архивы.

Не генерировать новую CMS, авторизацию, загрузчик файлов и произвольный page builder на каждом проекте. Они дают мало ценности для редактирования прайса и резко увеличивают ответственность.

Стартовая инвестиция: ориентировочно **24–40 часов** на общую тему, 4–5 схем, адаптер Vite, экспорт, упаковку и проверки. Отдельно 1–2 пилотных сайта. Это оценка до прототипа; не включать её полностью в цену первого клиента и не обещать конвейерную скорость до проверки.

## Что клиент редактирует

Панель по-русски с понятными подписями, а не редактор произвольного HTML. Наличие и качество локализации выбранного выпуска проверить на пилоте; недостающие подписи наших форм перевести самим.

| Раздел | Поля | Границы |
|---|---|---|
| Общие сведения | Телефон, email, адрес, часы, ссылки мессенджеров | Разметка и дизайн остаются фиксированными |
| Прайс | Название, цена, «от», единица, пояснение, порядок, видимость | Без складского учёта и формул произвольной сложности |
| Галерея | Изображение, подпись/alt, порядок | Ограничения типа, веса и количества; адаптивные размеры |
| Акции | Заголовок, описание, фото, начало/окончание, публикация | Не обещать автоснятие без проверки времени и кеша |
| Работы/товары, если заказаны | Название, описание, изображения, цена/запрос цены, категория | Витрина, без корзины, оплаты и остатков |

Прайс и небольшую галерею хранить повторяемыми полями; большие коллекции — отдельными записями/страницами. Для первой версии ограничить редактируемый каталог примерно 30 карточками и 3–5 полями на карточку; больший объём оценивать отдельно. Это коммерческая граница пакета, не технический лимит Grav.

Редактору не давать установку плагинов, изменение кода, системной конфигурации и шаблонов. Отдельный технический аккаунт передать владельцу. Реальные права выбранного выпуска и запреты на прямые API-запросы проверить при приёмке.

На сайте с CMS изменения видны после сохранения и обновления кеша. Старый статический ZIP не синхронизируется с CMS. В статическом варианте акции по календарю автоматически не снимаются: нужен новый выпуск либо отдельно согласованная реализация; не маскировать это клиентским JS как полноценную публикацию.

## Поставка и установка

**Установка и запуск включены в основной пакет.** Для клиента готовность означает, что сайт открывается на его домене, корректно работает на телефоне, контакты ведут к нужным адресатам, а заказанная CMS позволяет менять согласованные поля.

**Клиенту передаём один выбранный рабочий пакет**, исходники отдельно и короткую инструкцию. Статический снимок CMS-версии можно включить отдельным резервным архивом с датой, но не как второй обязательный runtime.

### Хостинг как часть услуги

Проверка белорусских провайдеров, 19.11.2026:

| Провайдер | Публичная цена | Что подтверждено страницей |
|---|---|---|
| [ActiveCloud Mini](https://www.activecloud.by/hosting/linux/) | 68,28 BYN за год; эквивалент 5,69 BYN/мес. При оплате одного месяца указано 6,56 BYN | 2 сайта, 2 ГБ диска, PHP 5.2–8.4, Apache/Nginx, .htaccess, бесплатный SSL и автоматические резервные копии |
| [HB.BY](https://hb.by/) / [Unix](https://hb.by/solutions/hosting/unix) | На главной от 5,94 BYN/мес. при оформлении на год; арифметически 71,28 BYN/год | Старт: 1 сайт, 10 ГБ; PHP 8.3/8.4/8.5, OPcache, Apache/Nginx и mod_rewrite, бесплатный SSL, ежедневные резервные копии |

Цены сняты с публичных страниц; акции, окончательный счёт, налоги и стоимость продления перепроверить перед оплатой. На странице HB.BY динамические цены карточек не извлеклись: 5,94 BYN — опубликованный ориентир главной, не проверенная корзина заказа. Хостинг не покупался, поддержка провайдеров не запрашивалась, Grav на их серверах не устанавливался.

Вывод: PHP уже входит в обычный виртуальный хостинг; отдельный VPS для выбранной схемы не закладываем. По этим предложениям базовый год стоит порядка 70 BYN, а не требует отдельной дорогой инфраструктуры. Для внутренней сметы ориентироваться на 70–120 BYN/год с запасом на подходящий тариф; запас — наше допущение. Ранее заложенные $60/год остаются верхним бюджетным резервом, а не обязательной стоимостью хостинга. Не переводить BYN в USD без актуального курса при подготовке КП.

Лёгкость установки пока подтверждена архитектурно, не испытанием. Перед выбором стандартного провайдера развернуть один CMS-пилот в тестовом периоде: проверить точную версию PHP, все расширения Grav, memory_limit, права записи, rewrite, загрузку/обработку фото, работу кеша и восстановление. Для начала рассмотреть ActiveCloud Mini и HB.BY Unix Старт как кандидатов, а не гарантированно совместимые тарифы. Не выбирать более дорогой CMS/WordPress/Bitrix-тариф только из-за названия: сначала проверить базовый.

Без CMS ставим чистую статику даже на тарифе с PHP — интерпретатор для её страниц не используется. С CMS хостер ведёт серверную среду, а обновления Grav/плагинов и проверка совместимости остаются задачей владельца сайта или отдельно нанятого исполнителя. Это основное отличие по сопровождению. Не превращать весь парк сайтов в нашу постоянную обязанность ради экономии на аккаунтах.

- Для стандартных пакетов включать первый год обычного виртуального хостинга. В расчёте цены ниже заложен бюджет до $60/год; фактический тариф и стоимость фиксируются в КП до оплаты. Если подходящий тариф дороже, итоговую цену согласовать заранее. Это наш бюджет, не проверенный тариф провайдера.
- По возможности использовать существующий подходящий хостинг клиента: проверить его до договора и скорректировать смету, чтобы не продавать второй оплаченный хостинг без необходимости.
- Аккаунт, восстановление доступа и платёжные реквизиты — клиента. На первый год можно оплатить выбранный тариф в рамках договора; после передачи продление клиент оплачивает напрямую провайдеру. Наш административный доступ — отдельный и отзываемый.
- Подключение существующего домена включено. При новом домене регистрационные действия включены, сама регистрация и ежегодное продление оплачиваются отдельно по согласованной фактической цене регистратора и указываются в полной смете. Домен регистрируется на клиента.
- Не размещать всех клиентов внутри одного нашего аккаунта/VPS. Общий сервер создаст постоянную эксплуатационную услугу, от которой текущая модель должна оставаться независимой.
- До переключения DNS сохранить настройки и проверить почтовые записи MX/TXT. Существующую почту сохранить; перенос почтовых ящиков и сложная миграция сервера оцениваются отдельно. Подготовить откат на предыдущий сайт.
- Настроить доступное у провайдера резервное копирование, проверить восстановление, передать дату окончания оплаченного периода и инструкцию продления. Не обещать постоянный мониторинг с нашей стороны.

В паспорте проекта фиксировать владельца хостинга/домена, провайдера, тариф, начало/конец оплаченного периода, ориентир продления, контакт для уведомлений, резервные копии и ответственного за обновления. Пароли хранить отдельно от общей таблицы.

| Без CMS | С CMS |
|---|---|
| HTML страниц, собранные CSS/JS, картинки, favicon, sitemap/robots, необходимые редиректы | Grav + Admin и обязательные зависимости, наша тема с готовыми assets, blueprints и контент |
| Любой согласованный статический HTTP-хостинг | Совместимый PHP-хостинг с HTTPS, rewrite и правами на нужные каталоги |
| Без админки, серверной БД и нашей инфраструктуры | Без отдельной MySQL/PostgreSQL и без Node.js на сервере |
| Изменение данных = редактирование исходников/новая сборка | Изменение согласованных данных = сохранение в панели |

В отдельном source-архиве: шаблоны, стили/JS, контент, lock-файлы, конфигурация сборки, лицензии, инструкция для следующего разработчика. В публичный webroot не класть source-архив, резервные копии, секреты, логи и внутренние инструкции. Учётные данные передавать отдельно, не общим паролем для всех клиентов.

По официальной документации текущая линия Grav 2.x требует **PHP ≥ 8.3.11**, расширения PHP и корректную конфигурацию сервера. Для типовой поставки выбираем Apache/LiteSpeed, поддерживающий .htaccess; Nginx — отдельная проверенная конфигурация. Не использовать старые требования Grav 1.7. [Требования](https://learn.getgrav.org/2/basics/requirements), [готовый ZIP с Admin](https://learn.getgrav.org/2/basics/installation), [стабильные загрузки](https://getgrav.org/downloads).

Перед продажей CMS уточнять доступный PHP и расширения, права записи, лимиты загрузки/памяти и возможность резервного копирования. Полный установочный пакет собираем мы с зависимостями: клиент не запускает Composer или сборку админки. Первый технический пользователь создаётся под контролем установщика до открытия сайта публике; не оставлять публичную неинициализированную установку.

Обновление нашей темы не должно затирать изменённые клиентом страницы, медиа, аккаунты и конфигурацию. Перед обновлением — резервная копия и проверка восстановления. Не обновлять весь каталог сайта поверх старого архивом начального состояния.

Переход со статического пакета на CMS возможен на базе наших исходников, но это платная работа: сверить внесённые после передачи изменения, настроить поля, перенести данные и проверить хостинг. Доплата за поздний переход может быть выше первоначальной опции CMS.

## Формы и обслуживание

Статический HTML не умеет сам отправлять email или Telegram-заявки. В базовую статику входят работающие ссылки телефона/мессенджера; форма — отдельный согласованный обработчик PHP на хостинге клиента или внешний сервис на его аккаунте. Секреты SMTP/Telegram нельзя класть в JS. Отправка заявки не должна зависеть от нашего общего сервера.

Для CMS-пакета обработчик формы тоже отдельная функция: доставка, ограничения загрузок, защита от спама и обработка ошибок проверяются отдельно. Для первого дешёвого пакета можно обойтись без формы, если контактные кнопки решают задачу.

Без обязательной подписки на нашу поддержку — реалистичная модель. «CMS никогда не нужно обновлять» — нет: остаются PHP, CMS и плагины. Зафиксировать, кто отвечает за обновления и резервные копии: клиент/его специалист, хостер в пределах услуги или мы по разовому заказу. Отдельный VPS, Docker и парк сайтов на нашем аккаунте не являются стандартной поставкой.

## Проверка перед принятием стандарта

Сделать один пилот: услуги + 10 строк цен + 12 фото + две акции. Из него получить обе поставки и развернуть на двух чистых площадках: статический сервер без PHP и обычный совместимый PHP-хостинг.

Приёмка:

- В CMS редактор меняет цену, фотографию и акцию, добавляет элемент и меняет порядок без доступа к коду и без нашей сборки. Проверяются ограничения роли и сохранность данных после обновления темы.
- В статике весь основной контент присутствует в исходном HTML; работающие меню/галерея, контакты, вложенные маршруты, 404, изображения и метаданные. Нет ссылок на localhost, runtime CMS или dev-CDN.
- Проверяются мобильные размеры, длинные тексты/цены, пустая галерея, крупное фото, русские имена файлов, кеш и даты акций. Картинки пережимаются, шрифты и assets размещаются локально при наличии права на распространение.
- Экспорт берёт только опубликованные публичные маршруты. Админка, API, черновики, аккаунты и закрытые медиа не попадают в статический ZIP; все зависимости картинок/CSS/JS скопированы.
- Смена домена, повторная установка из ZIP и восстановление резервной копии проходят по короткой инструкции. CMS-версия не содержит старого index.html, который может перекрыть PHP-страницы.
- Лицензии ядра, плагинов, шрифтов и изображений сохранены. В поставке нет паролей, токенов и лишних платных зависимостей.

После успешного пилота оформить reusable starter и инструкции для агента. До этого Grav — выбранный кандидат для стандарта, а двухрежимная упаковка — проектируемая архитектура, не внедрённая возможность этого репозитория.
